A from-scratch operating system in Rust

The OS that runs rustc — and builds itself.

Ferrix has its own kernel, drivers, file systems, C library, shell and Wayland desktop, all in Rust. It runs unmodified Linux programs on them: rustc, cargo, git, curl and Google Chrome. A fleet of AI agents wrote it.

Proof, not claims

Every headline on this page is a gate: a command that boots Ferrix in QEMU and fails unless the system does what it says. These lines are copied from the gates' serial logs.

cargo xtask test-rustc

Boots Ferrix with a btrfs volume holding the rust-lang.org release of rustc and Debian's glibc. It compiles hello.rs through cc, collect2 and rust-lld: five programs nobody here wrote, four execves deep, over some 350 MiB of shared libraries mapped from disk. Then it runs the result.

cargo xtask test-selfhost

Gives Ferrix that toolchain, this repository and its crates on one btrfs volume. Inside the guest it runs cargo xtask build, the same command you run on a Linux host. Then it boots the image Ferrix built.

x86_64: Ferrix built its own image, and it booted

Every boot also checks itself. The memory map is compared with the loader's allocations. The allocators are hammered and must give every frame back. Four processors increment one counter and must reach exactly 100,000. Each check carries a negative control that must be seen to fail.

A whole system, not a kernel demo

The kernel

UEFI hand-off with no bootstrap assembly. Higher-half memory where no mapping is both writable and executable. SMP with TLB shootdown, preemptive tasks under an EEVDF fair scheduler, and cgroups.

Linux programs, unchanged

The Linux system-call ABI: threads, futexes, signals, fork/execve, epoll, ptys and job control. Dynamic linking goes through glibc's own ld-linux. 32-bit x86 programs run too.

Drivers in ring 3

virtio-blk, -net, -gpu, -input and -console are user programs started by devmgr. They sit behind an IOMMU (VT-d on x86-64, SMMUv3 on AArch64) and restart after a crash.

btrfs, read and write

/ is a persistent btrfs volume, written with a log tree that fsync replays. The host's btrfs check judges it, including after QEMU is killed mid-write, across 249 seeds.

Networking

TCP, UDP, IPv6, raw and packet sockets, and netlink. curl fetches over HTTPS, git clones inside the guest, and SSH is served from it.

A userland of its own

ferrousli, a C library in Rust that answers most of POSIX.1-2024. zinc, a zsh-compatible shell that runs oh-my-zsh. An init with svc, and the uutils tools.

A desktop

hyprix, a Hyprland-shaped Wayland compositor written from scratch. It reads a real hyprland.conf, tiles windows, composites on the GPU through virgl, and runs Chrome with video and sound.

Real hardware

Boots an STM32MP157D-DK1 board from its SD card (Cortex-A7), and a Google Pixel 7 on all eight cores. Under QEMU, --accel auto runs it on KVM, HVF or WHPX.

How it's built: a fleet of AI agents

Ferrix is written by many Claude sessions working at once, each in its own git worktree. A human product owner sets scope and priorities. One coordinator session orders the landings, and a certification consultant reviews every change to the kernel core.

A change lands only when a gate passes, and a gate means booting the whole system. There is a written convention for every mistake that cost work. The roadmap, backlog and conventions are all in the repository, including the failures.

We think it is the most complete answer yet to the question "how far can agents go on a real systems project?", and we built it in the open so you can check.

Try it

You need Rust and QEMU. It runs on Linux, macOS and Windows hosts.

# clone and boot to a shell on the serial console
git clone https://github.com/SetZero/ferrix && cd ferrix
cargo xtask run --arch x86_64

# the Wayland desktop with a terminal
cargo xtask run-compositor

# ...with Chrome, rustc and cargo (fetch them first, see the README)
cargo xtask run-compositor --everything

# every gate CI runs
cargo xtask check

Quit QEMU with Ctrl-A x. The README covers every flag, the board, and Windows.

FAQ

Is Ferrix based on Linux?

No. The kernel, drivers, file systems, C library, shell and compositor are written from scratch in Rust. Ferrix implements the Linux system-call ABI, so unmodified Linux programs run on it. uname -s says Ferrix.

Was it really written by AI?

Yes, by a fleet of Claude sessions under a human product owner. Nothing about it is hidden: the process, the landing rules and the post-mortems are in docs/.

Can I use it every day?

Not yet. It is a research and hobby system. It runs a desktop, a browser and a compiler, but authentication, namespaces and seccomp are still being written.

How can I help?

Boot it, break it and file what you find. Star the repository if you want to follow along. Each release is announced on GitHub.
