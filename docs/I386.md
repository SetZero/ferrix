# The 32-bit x86 ABI: i386 programs on the x86-64 kernel

Version 1, written on 2026-09-26 when the customer asked for the next step
towards Steam to start. `docs/ROADMAP.md` stage 22 lists what Steam needs
"in the order it can be tested", and the first item is this: the Steam
client is an `i386` program, and so is every 32-bit Wine that Proton runs a
32-bit Windows game in. Sound (`docs/AUDIO.md`) is already under way, and
XWayland is counted in stage 19's remainder, so this is the part of stage 22
that nobody had started.

## 1. What this is, and what it is not

Linux calls it IA32 emulation (`CONFIG_IA32_EMULATION`): a 64-bit kernel
runs 32-bit x86 programs unchanged, in the processor's compatibility mode,
through the `i386` system call table, with every structure laid out as a
32-bit program expects. Ferrix already has a 32-bit Linux ABI, ARMv7-A's,
but that one runs on a 32-bit kernel, where `usize` is the program's word.
Here the kernel is 64-bit and the program is not, so every width the
program sees has to be chosen on purpose.

It is x86-64 only: the Arm architectures have no 32-bit x86 program to run.
It is not Wine's `modify_ldt` segments, `vm86`, 16-bit code, `ptrace`, or a
32-bit vDSO. §5 says which of them Steam may still need.

**The exit**, in the order it can be tested:

1. **I1:** a 32-bit program enters compatibility mode, makes system calls
   through `int $0x80`, and exits. The boot runs one, built at boot from a
   hand-assembled i386 image like `USER_TEST_PROGRAM`.
2. **I3:** Alpine's static musl `busybox` for `x86`, unchanged, passes
   `cargo xtask test-shell` and `test-vfs` on x86-64.
3. **I4:** Debian's i386 `busybox` passes `test-shell` on its own
   `ld-linux.so.2` and `libc.so.6`, and an i686 Rust `std::thread` program
   passes `test-threads`.

After that, what is left is whatever the Steam runtime and client find
missing (§5), found by running them.

## 2. What the programs actually do

Read from musl 1.2.5 (`~/.local/share/ferrix/ferrousli-ref`) and Linux's
`arch/x86/entry/syscalls/syscall_32.tbl` (the UAPI header
`asm-x86/unistd_32.h` in the local QEMU checkout).

* **The way in is `int $0x80`.** musl's `__sysinfo` defaults to a stub of
  `int $128; ret` (`src/internal/i386/defsysinfo.s`), and is replaced only
  when the kernel passes `AT_SYSINFO`. glibc's i386 port has the same
  fallback, `_dl_sysinfo_int80`. A kernel that passes no `AT_SYSINFO` is
  therefore entered by `int $0x80` alone, and the fast `SYSENTER` and
  compatibility-mode `SYSCALL` paths are optional. Ferrix leaves them out
  (§3.3).
* **The thread pointer is a segment.** musl's `__set_thread_area` calls
  `set_thread_area` (243) with `entry_number` −1 and a flat 4 GiB data
  descriptor based at the thread block, then loads `%gs` with the entry the
  kernel chose. If that fails it falls back to `modify_ldt` (123) and
  selector 7. glibc does the same without the fallback. So compatibility
  mode needs three thread-local descriptors in the GDT, per thread, swapped
  on every switch. Linux's are entries 12 to 14.
* **Registers:** the number in `EAX`; the arguments in `EBX`, `ECX`, `EDX`,
  `ESI`, `EDI` and `EBP`; the result in `EAX`. A 64-bit argument is two
  registers, low half first, with **no** alignment to an even register.
  ARMv7-A's EABI aligns such an argument to an even pair, so the arm
  handlers' reassembly cannot be reused as it is.
* **Layouts** differ from ARMv7-A's more often than they agree. `struct
  stat64` is 96 bytes on i386 and 104 on ARM, because i386 aligns a
  `long long` to four bytes. `epoll_event` is packed on both x86 ABIs.
  Anything holding a `long` or a pointer (`iovec`, `msghdr`, `sigaction`,
  `stack_t`, `siginfo`, `rlimit`, `rusage`, `sysinfo`, `statfs`) is 32-bit
  words. And there are the i386-only multiplexers: `socketcall` (102) and
  `ipc` (117), which older glibc builds, the Steam runtime's among them,
  still issue; `mmap` (90) taking a pointer to its six arguments; and the
  pre-`rt` `sigaction` and `sigreturn`.
* **time64:** musl 1.2 on i386 uses the `_time64` calls (403 onward) first,
  as it does on ARMv7-A, so the 32-bit `timespec` calls are a fallback, and
  ARMv7-A already answers most of them.

## 3. The design

### 3.1 The GDT takes Linux's order and Linux's numbers

Ferrix's GDT is Linux's in shape, but one slot shorter at the front, so
every user selector is eight below Linux's: 32-bit user code `0x1b`, user
data `0x23`, 64-bit user code `0x2b`, against Linux's `0x23`, `0x2b` and
`0x33`. Its 32-bit user code descriptor exists only to put the other two
where `SYSRET` computes them. It has no size bit, no granularity and a limit
of zero, so compatibility mode cannot run in it.

Decision: **take Linux's layout exactly**. Entry 1 is an unused 32-bit
kernel code slot, 2 is kernel code (`0x10`), 3 kernel data (`0x18`), 4
32-bit user code (`0x23`), 5 user data (`0x2b`), 6 64-bit user code
(`0x33`), 8–9 the TSS, 10–11 an empty LDT slot, and 12–14 the thread-local
descriptors (`0x63`, `0x6b`, `0x73`). The user code and data descriptors
become flat 4 GiB segments (`G`, `D/B`, limit `0xFFFFF`), which 64-bit mode
ignores and compatibility mode enforces.

The reason for matching numbers rather than only order: programs compare
them. A signal handler reads `uc_mcontext` `cs`; Wine keeps the 32-bit and
64-bit code selectors to switch between modes; debuggers print them. Linux
is the standard (`docs/BACKLOG.md`, decision of 2026-09-13: Linux wins where
it and POSIX differ), and a selector that differs from Linux's is a
difference a program can see.

### 3.2 The ABI of a call is its entry's

Linux decides by the entry, not by the process (`in_compat_syscall()`). A
call through `int $0x80` is an i386 call even from a 64-bit program, and a
`SYSCALL` from 64-bit mode is an x86-64 call even from a process whose image
was 32-bit. Ferrix does the same. `crate::trap::SyscallArgs` gains an `abi`
field, `Abi::Native` or `Abi::Compat`, which the entry that read the
registers fills in. The certified item's dispatcher decodes the number with
the table that field names (`arch::decode_syscall(abi, number)`), behind the
same Spectre clamp against that table's end. So the personality never sees a
raw number, and the item still holds the only decoding
(`docs/certification/FINDINGS.md`, F-09).

Arguments are zero-extended from 32 bits into `SyscallArgs`, as ARMv7-A's
entry already does. Every `int`-typed argument is therefore right as it
is, because the handlers truncate those. A `long` or `off_t` argument that
the handler reads as a native signed word is not, and neither is a structure
the handler reads in native words (`file.rs` reads `iovec` as
`size_of::<usize>()` words). Those are fixed per call in I3, by the handler
asking the call's word width rather than the build's. Until a call has been
read for that, its i386 number is **not mapped**: it answers `ENOSYS`, which
`report_unanswered` names, rather than being dispatched to a handler that
would silently misread it. This is `nr.rs`'s rule, "absent rather than
guessed", applied to widths as well as numbers.

### 3.3 The ways in and out of compatibility mode

* **In:** vector `0x80` becomes a DPL-3 interrupt gate. It classifies as
  `Trap::SystemCall` (it already does), and `arch::system_call` reads the
  i386 registers into `SyscallArgs` with `Abi::Compat`. A 64-bit program's
  `int $0x80` takes the same path, as on Linux.
* **Out: always `IRETQ`, never `SYSRETL`.** On AMD, `SYSRET` does not
  reload `SS`'s cached attributes when the kernel's `SS` is null, which an
  interrupt from ring 3 leaves it, and 32-bit code, unlike 64-bit code, uses
  them (Linux's `X86_BUG_SYSRET_SS_ATTRS`, worked around there on every
  switch). `IRETQ` loads `SS` whole. The trap path already leaves by
  `IRETQ`, and so does everything else that enters 32-bit code: the first
  entry of a 32-bit program, and an `execve` of a 32-bit image from a 64-bit
  `SYSCALL`, build a frame and leave through the trap stub's restore path, as
  `rt_sigreturn` already does (`resume_context`). So the hot `SYSCALL` stub
  is not touched, and entering compatibility mode takes no new assembly.
* **`DS` and `ES`:** long mode ignores them. Compatibility mode faults on a
  null one, and `IRETQ` to ring 3 nulls any data selector whose DPL is
  below 3. Every return to 32-bit code therefore loads both with user data
  first. In I1 that is done on the way out. From I2 each task keeps its own
  `DS`, `ES`, `FS` and `GS` selectors, as Linux's `__switch_to` does, and the
  way out restores them.
* **The other two instructions are made harmless, not supported.** Once a
  real 32-bit code segment exists, any 64-bit program can far-jump into it.
  There, `SYSCALL` goes to `IA32_CSTAR` on AMD. That MSR is zero today, and
  zero would be a ring-0 jump to address zero on the program's stack. So
  `CSTAR` gets a stub that answers `-ENOSYS` without switching mode.
  `SYSENTER` faults when `IA32_SYSENTER_CS` is zero, as Linux leaves it
  without IA32 emulation. Ferrix writes that zero at boot rather than
  trusting firmware to have left one. Neither is how musl or glibc enter
  when there is no `AT_SYSINFO` (§2).

### 3.4 A 32-bit process's shape comes from its image

`execve` of an `ELFCLASS32`, `EM_386` image makes a compat process:

* **A 4 GiB address space.** The space's ceiling is `0xFFFFE000`, Linux's
  `IA32_PAGE_OFFSET`, set on `ferrix_vma::AddressSpace` so that `mmap`'s
  free-space search and `MAP_FIXED` both stop there. A reservation above
  4 GiB would have worked too, but `/proc/<pid>/maps` would show it.
* **Placement:** the stack top is just below the ceiling. A PIE's base and
  the dynamic linker's follow Ferrix's rule for native programs, two thirds
  and one third of the way up, but of the 4 GiB window rather than of
  `USER_VIRT_END` (`load::pie_base`, `load::interp_base`). Linux differs: it
  puts an ia32 PIE at `0x400000` (`ELF_ET_DYN_BASE`) and `mmap`s the linker
  below the stack. Ferrix keeps the linker below the program so the heap has
  the space up to the stack. Revisit in I4 if a 32-bit program cares where it
  lands, which a program with a large heap might.
* **The startup stack in 32-bit words:** `libs/kernel/ustack` already builds
  `Width::Bits32` for ARMv7-A. There is no `AT_SYSINFO_EHDR`, because the
  vDSO is a 64-bit ELF and is not mapped, and no `AT_SYSINFO` (§2).
  `AT_HWCAP` is `CPUID.1:EDX`, as for x86-64. `AT_PLATFORM` is `i686`,
  Linux's `COMPAT_ELF_PLATFORM`.
* **Entry** at the image's entry point in 32-bit user code (§3.3).
* **Signals:** i386 `sigframe` and `rt_sigframe` from I2. Until then, a
  compat process whose handled signal would need a frame is ended with
  `SIGSEGV`, which is what Linux does when it cannot build one. A signal's
  default action works in I1.

The image's ABI travels in the loader's `Loaded` and the process's
`Startup`, and it is how the program is first entered. Once the program runs,
its mode is its thread's code selector, which the signal code reads
(`UserContext::is_compat`) and `fork` will copy with the rest of the frame
(I2). System call decoding reads neither (§3.2). A native process, which
`devmgr` starts with a 64-bit handle, cannot be 32-bit: `load_native`
refuses an `EM_386` image.

### 3.5 Thread-local descriptors and segment selectors (I2)

Each thread keeps three `user_desc`-shaped TLS entries and its four data
selectors. A switch to a thread writes its entries into this processor's
GDT slots 12–14 and loads its selectors, `GS` last, around a `swapgs`, since
loading `GS` in ring 0 replaces the kernel's own `GS` base. That is Linux's
`load_gs_index`. `set_thread_area` with −1 picks the first free slot and
writes the number back. `clone` with `CLONE_SETTLS` from a compat call takes
a `user_desc` pointer, not a base. `get_thread_area` reads an entry back.
`modify_ldt` stays `ENOSYS`: musl falls back to it only when
`set_thread_area` fails, and Wine's need for it is §5's.

**Gates.** I1–I4 change the image (`kernel/`, a kernel-side crate), so each
runs the table's "anything the image contains" row, plus x86-64 under

## 5. Open questions, for when they are reached

1. **`modify_ldt`.** 32-bit Wine keeps its TEB in `%fs` through an LDT
   descriptor, and Proton's older 32-bit path needs it. That means a
   per-process LDT, the `LDT` slot of §3.1, and a load on switch. It is I5's,
   and sized when Wine is run.
2. **A 32-bit vDSO.** Not needed by either libc (§2). Linux has one, and a
   program that reads `AT_SYSINFO` unconditionally would need it. Nothing
   found so far does.
3. **The Steam client may not stay 32-bit.** The roadmap already allows for
   a 64-bit client arriving first. If one does, I1–I4 are still Proton's and
   still 32-bit games', and I5 shrinks.

## 6. Where it stands

**2026-09-26: I1 is done** (8 points, as estimated), on branch `i386-abi`.
What is on it:

* The GDT is Linux's, entry for entry and selector for selector (§3.1): the
  64-bit user code selector is now `0x33`, not `0x2b`, and the SMP
  trampoline's GDT follows the kernel's code and data to `0x10` and `0x18`.
* `libs/proto/linux-abi` has `nr::i386` and `from_i386`, generated from
  `asm/unistd_32.h`, with 18 calls mapped: those whose handlers read nothing
  at a native width (`read`, `write`, `close`, `exit`, `exit_group`, the
  identity calls, `uname`, the `dup`s, `sched_yield`, `restart_syscall`).
  A host test holds each number to the header and to what ARMv7-A's table
  means by it.
* `SyscallArgs` carries `Abi`, and the item's dispatcher decodes through
  `arch::decode_compat_syscall` for `Abi::Compat`, behind its own clamp. The
  native ABI's range is reachable only from the native entry.
* `ferrix_vma::AddressSpace::set_high` and `AddressSpace::set_ceiling` give a
  32-bit program's space its 4 GiB ceiling. The loader places, and `execve`
  empties, up to the space's ceiling rather than `USER_VIRT_END`.
* The boot's trap check runs four programs: an `EM_386` image that writes
  "hello from i386" and checks `-EBADF` and `-ENOSYS` arrive whole in `EAX`;
  a 64-bit program whose `int $0x80` `getpid` must equal its `SYSCALL`
  `getpid`, and whose `dup` must ignore the upper half of `RBX`; and a far
  return into 32-bit code followed by `SYSCALL`, then by `SYSENTER`. Under
  TCG those answer `-ENOSYS` and `SIGSEGV`; under KVM on the Ryzen 9 9900X
  host, `-ENOSYS` (the `CSTAR` stub, through a real `SYSRETL`) and `SIGILL`
  (AMD has no `SYSENTER` in long mode).
* Assembly: six lines for the `CSTAR` stub and six for `DS`/`ES` on the way
  out, recorded in `scripts/data/asm-allowlist.json`. The first entry into 32-bit
  code first had a routine of its own, 27 lines; it now resumes a built frame
  through the trap stub's restore path instead. The tree is at 1587 of its
  1600 lines.

Gated on 2026-09-26 by the image row: `check`, the release build of all
three architectures, the four boots, x86-64 under KVM, `test-shell` with
zinc and the ferrousli, musl and glibc busyboxes, `test-vfs` with the
ferrousli and musl ones, `test-threads --arch all`, and Debian's dynamic
busybox on glibc's loader on all three architectures and on ferrousli's on
x86-64. The musl `test-shell` hit FX-0905 once, in the boot's quota
self-check, and passed on its rerun (`docs/BACKLOG.md` has the row).

**Known limits, each I2's or I3's:** a compat process cannot `fork`
(`ESRCH`: the trap path has no `UserRegs` to give a child yet); a handled
signal ends it with `SIGSEGV`; `DS` and `ES` are forced to user data on
every return to 32-bit code rather than kept per task; every i386 call past
the 18 above is `ENOSYS`, so no real i386 program runs yet.
